# 思考再干

用户任务：$ARGUMENTS

按以下 6 步流程执行（全程主 agent 自己跑，不派 sub-agent）：

## Step 1 · 捋清边界
明确 3 项清单：
- **该做什么**：用户直接要的功能
- **不该做什么**：用户没要求但容易被诱惑做的（避免 scope creep）
- **范围冲突**：跟现有约定 / 已有产物 / 已固化设计有没有冲突

## Step 2 · 做计划
设计实现方案：
- 涉及哪些文件（改 / 新增 / 删）
- 端点契约（输入 / 输出 / 错误码）
- 数据存储 / 依赖 / 副作用
- 实现顺序

## Step 3 · 反思计划
对比「计划」vs「用户原始任务」vs「Step 1 边界」：
- 能不能完成用户目标？
- 有没有越界 / 漏做？
- 有没有技术风险 / 不可达点？
任一不符合 → **回 Step 2 改计划**。

## Step 4 · 实现
按通过的计划写代码：
- 改一处提交一处（小步 commit）
- 不存根（pass / TODO / NotImplementedError 禁止）
- 不假实现（InMemoryRepository / mock DB / 硬编码禁止）

## Step 5 · 反思实现
对比「实现」vs「计划」vs「用户真实需求」：
- 跟计划一致吗？
- 能跑通吗（编译 / 测试）？
- 跟用户真实需求对齐吗？
任一不一致 → **回 Step 4 改实现**。

## Step 6 · 双层校验

### Layer A · 6 维度静态校验（基础）
| 维度 | 检查点 |
|------|--------|
| 代码质量 | 无存根 / 无重复 / 命名一致 / 单一职责 |
| 可靠性 | 异常处理 / 重试兜底 / 幂等性 / 边界条件 |
| 安全 | 权限校验 / 输入校验 / 注入防御 / 敏感信息不外泄 |
| 性能 | 时间复杂度 / 关键路径无瓶颈 / 资源占用合理 |
| 可维护性 | 注释充分 / 测试覆盖 / 调试手段 / 扩展点 |
| 文档同步 | README / changelog / API 文档反映最终接口 |

任一维度 P1 → 标注 warning（不阻塞交付）

### Layer B · E2E 浏览器测试（最重要）🎯
**主 agent 自己跑**（不派 e2e-tester）：

1. **启动应用**：
   ```bash
   # 二选一
   docker compose up -d
   # 或
   npm start &  # 或 python main.py &
   ```
2. **写 playwright 脚本**——针对用户真实用例设计 **1~3 个核心 journey**（按任务复杂度灵活调整，如「登录 → 创建订单 → 验证」）
3. **跑测试**：
   ```bash
   npx playwright install chromium  # 首次安装
   npx playwright test --reporter=list
   ```
4. **断言**：每个 journey 必须 PASS（含截图 + HTTP 状态码 + DOM 元素存在）
5. **失败处理**：任何 journey FAIL → **P0 硬阻塞 → 回 Step 4 重写**（实现 bug）

**环境受限处理**：
- 容器/CI 无浏览器：使用 `playwright-chromium` headless
- 完全无 GUI 环境：标注「E2E 跳过 - 环境受限」+ 输出**手动验证清单**（步骤 + 期望结果 + 截图位置）

## 交付
完成后摘要：
- 改了哪些文件（路径列表）
- 关键 commit
- 6 维度校验结论（每维度 1 句话）
- E2E journey 结果（PASS/FAIL 数 + 截图路径）
- 遗留事项（E2E 跳过原因 / P1 warning）
